Start / Overview

morsec documentation

morsec lets a coding agent use your API keys, database passwords and tokens without ever seeing them. The agent holds references like ms://stripe/test. The values stay in your macOS keychain, and msd, a daemon running as you, adds them at the last moment.

Start / Install

Install

You need an Apple silicon Mac with macOS 13 or later. Every channel installs the same four programs: ms, mors (the same command), msd and ms-shim. They are signed with Developer ID team 554MCRUAKK and notarized.

$ brew install csakash/tap/morsec

msd's LaunchAgent points at Homebrew's stable opt/morsec path, so upgrades are picked up after a restart.

$ npm install -g morsec

Needs an arm64 Node.js 18 or later. The binaries come in morsec-darwin-arm64. Neither package runs anything at install time.

$ curl -fsSL https://github.com/csakash/morsec/releases/latest/download/install.sh | sh

Installs into ~/.local/bin (or MORSEC_INSTALL_DIR) without sudo. Before installing, it checks the checksums, their minisign signature when minisign is installed, each code signature and team, and notarization. Add --version 0.2.0 to pin.

Read before you run. Download install.sh, SHA256SUMS and SHA256SUMS.minisig from the release, check them as Verify a download shows, then run sh install.sh.

Start / Quickstart

Quickstart

One command protects a project. Run it inside the project folder, before you start an agent there.

1. Run ms init in your project

$ cd ~/code/shop$ ms init

The first time, it creates the vault in your login keychain, generates the local certificate authority and starts msd as a LaunchAgent. Then it protects the project:

  1. finds the secrets in the project's .env files (.env, .env.production, apps/web/.env and so on);
  2. moves them into the vault and rewrites each line as a reference, such as STRIPE_SECRET_KEY=ms://shop/stripe-secret-key;
  3. asks you once, with Touch ID, to let the keys it recognises reach their services (Stripe keys to api.stripe.com, and so on);
  4. connects Claude Code and Codex if it finds them (--no-connect skips this), and opens the dashboard (--no-open skips that).

It ends with a short summary:

Project    shop  (~/code/shop)Found      14 secrets in 3 filesProtected  12, ready to useNeeds you  2 have no known service yet: ms rules shop/session-secret --add-host <host>In code    1 key written straight into src/lib/stripe.ts:4 (move it into .env, then ms init)

2. Finish what it lists

  • Needs you: a key morsec doesn't recognise allows nothing yet. Say where it may go with ms rules <key> --add-host <host>.
  • In code: keys written straight into source files are reported with file and line, never changed. Move each into .env and run ms init again.

Values already in git history stay readable there. The summary names the files that were ever committed. Rotate those keys at the provider, then store the new value with ms set <key>.

3. Run your app through morsec

Your .env now holds references, so start your app with ms dev. It asks for Touch ID once per run.

$ ms dev -- npm run dev

4. Start a new agent session and check

$ ms doctor  ✓ msd identity verified · cc.morsec.msd · team 554MCRUAKK  ✓ claude-code routes through morsec

The agent sees only references. When it calls a key's service, msd swaps the real key in on the way out. ms log shows every use.

New repo with no secrets yet? Put the real values in a .env that is in .gitignore, then run ms init. Each time you add a secret, put it in .env and run ms init again; it only picks up new values. Don't paste keys into an agent's chat.

Run in your home folder, or with --machine, ms init only sets up this Mac. ms status says whether morsec is on and how many secrets it protects.

Start / Set up by hand

Set up by hand

The same thing one key at a time, for keys that don't live in a project's .env, or for run-mode keys such as database passwords and deploy tokens.

1. Add your secrets

Type one in (hidden input), or move a whole .env in. Import shows a review table first, then stores the values and rewrites the file with references.

$ ms add stripe/test --tier test$ ms import .env

ms add keys are production tier unless you say otherwise, and ms add never replaces a key that exists: that is ms set.

Values already in git history stay readable there. Rotate any key that was ever committed, then import the new one.

2. Say where each key may go

$ ms rules stripe/test --add-host api.stripe.com

3. Connect your agent and check

$ ms connect claude-code --env STRIPE_API_KEY=ms://stripe/test$ ms doctor  ✓ msd identity verified · cc.morsec.msd · team 554MCRUAKK  ✓ claude-code routes through morsec

Start a new agent session. It sees STRIPE_API_KEY=ms://stripe/test. When it calls api.stripe.com, msd swaps the real key in on the way out.

Your projects / Projects

Projects

A project is a folder ms init has set up. Its keys are named after it and the variable, so STRIPE_SECRET_KEY in ~/code/shop becomes shop/stripe-secret-key. --name picks another project name, and --project <path> sets up a folder other than the current one.

What it reads, and what it leaves alone

  • Every .env file in the project, as deep as it goes.
  • Never .env.example, node_modules or other dependency folders, or anything behind a symlink.
  • Keys written into code are reported with file and line, never changed.
  • An existing CLAUDE.md or AGENTS.md gets a short note telling agents to keep ms:// references as they are. morsec never creates those files.

If you say no to the Touch ID approval, the secrets are still safe in the vault and the files still hold references. Run ms init again to approve. Running it again later is safe: it only picks up new values.

$ ms projects$ ms projects shop

ms projects lists your projects. With a name, it shows everything ms init did there, without values.

Undo a project

$ ms undo shop$ ms undo shop --key shop/stripe-secret-key

Writes each value back into the line ms init replaced, in its original quote style, and deletes the keys nothing else uses. A line you edited since is left alone and listed. It asks for Touch ID, and refuses inside an agent session.

Your projects / Run your app

Run your app with ms dev

After ms init, your project's .env holds references, so your own dev server needs morsec to work. Run it through ms dev, from your own terminal:

$ ms dev -- npm run dev
  • HTTP APIs: the command gets HTTPS_PROXY pointing at msd, so requests to your keys' services get the real key swapped in.
  • Database URLs and other run-mode values of this project are put in the command's environment.
  • One Touch ID per run. The sheet shows the command first, then the keys, the variables that get values, and that the command may reach other websites. Answer it in that terminal or with ms approve.
  • Only that command's processes can use the session, and it ends when your command exits, on ms stop, or when msd restarts.
  • Refused inside an agent session, and for agent programs: ms dev won't start a coding agent.

Node needs version 24 or later to send its requests through a proxy. ms dev sets NODE_USE_ENV_PROXY=1 and warns about older versions; on an older Node, references go out unswapped and the call fails rather than leaking.

Values in the environment are readable. Run-mode values that ms dev puts in your command's environment can be read by other processes running as you, and are inherited by anything that command starts. Only run code you trust under ms dev.

Your projects / Dashboard

Dashboard

$ ms dashboard$ ms dashboard shop

Opens a local dashboard in your browser, optionally on one project's page. msd serves it itself, on 127.0.0.1, with its fonts bundled: nothing is fetched from the internet. ms status --open opens it too.

ScreenWhat you can do
HomeApprove or deny the request an agent is waiting on, read each warning with its fix, stop or start morsec.
ProjectsSet up or re-scan a project folder, undo a project. On a key's page: show or copy its value, replace or delete it, change its websites, commands, git hosts, variables and SSH host keys, and undo its import.

AgentsConnect or disconnect Claude Code and Codex, and re-check msd's view of your agents.

  • Agents can't open it. ms dashboard refuses inside an agent session, and msd refuses connections from agent processes.

Concepts / References

References

A reference is the name of a secret in your vault, written ms://<name>. It is what goes in your .env, your agent's environment and its context window. It's safe to print, paste and commit.

For SDKs that check the format of a key, morsec can hand out a shaped placeholder such as sk_test_ms_… that msd maps back to the reference.

Concepts / Swap mode

Swap mode, for HTTP APIs

Connectors point the agent's HTTPS_PROXY at msd on loopback. For a host bound to a key, msd:

  1. terminates TLS with a certificate from your local morsec CA, whose name constraints cover only your bound hosts;
  2. replaces the reference in the configured place (a header, basic auth or a query parameter);
  3. strips any other credential the agent added;
  4. forwards over a fresh TLS connection, and writes a receipt.

A reference sent to a host it isn't bound to is blocked and recorded. Redirects carry no credentials, and cloud metadata and private address ranges are refused.

Concepts / Run mode

Run mode, for commands

For tools that aren't HTTP, such as psql, ssh, git and deploy scripts, msd runs the command for the agent. ms-shim sits first on the agent's PATH and hands calls with an ms:// reference to msd; anything else runs the real tool unchanged.

$ ms add db/staging --mode run --tier test$ ms rules db/staging --add-root ~/code/shop --add-env PGPASSWORD \    --add-command '["psql", "**"]'$ ms run --link-shims
  • Postgres: the password goes in a 0600 passfile only msd can reach, never in argv. Read-only rules set default_transaction_read_only=on.
  • SSH: msd is the SSH agent. The private key never leaves it.
  • git over HTTPS: msd is a credential helper for the bound host.

Output streams back through a redactor that also catches base64 and URL-encoded forms of the value. In a command pattern, * matches one argument and a trailing ** any number.

Concepts / Tiers and approvals

Tiers and approvals

test keys never prompt. production keys, the default for ms add, need your approval before each use, once or for the agent session.

The request appears in your terminal (ms approve, or ms approve --watch in a spare one) as plain text built from the real command, and you confirm with Touch ID. The approval is bound to the session, key, argument hash, directory and an expiry. Inside an agent session, ms approve refuses.

Concepts / Rules

Rules

Everything is denied by default. A key does nothing until you give it a target. Loosening a rule asks for Touch ID; tightening doesn't.

FieldWhat it does
hostsWhere a swap-mode key may be sent.
commandsWhich commands a run-mode key may be used with, as argument patterns.
tiertest or production.
session_ttl_secsHow long a session approval lasts.
read_onlyRun database commands in a read-only transaction.
disabledTurn a key off without deleting it.

A project's .morsec.toml can only tighten your rules for that repository.

Concepts / Receipts

Receipts

Every use, allowed or blocked, is one record: time, agent, session, key, mechanism, host or command, a hash and redacted copy of the arguments, the rule version, the approval and the result. Records are hash-chained and MAC'd with a vault key.

$ ms log --since 2h --result blocked$ ms log --verify  ✓ chain intact
Agents / Claude Code

Claude Code

Works in the terminal, the desktop app and the IDE extensions.

$ ms connect claude-code --env STRIPE_API_KEY=ms://stripe/test --dry-run$ ms connect claude-code --env STRIPE_API_KEY=ms://stripe/test

The connector sets the agent's environment and proxy, and puts ~/.morsec/shims first on its PATH for run mode. Add --with-mcp to expose your run commands as MCP tools. ms disconnect claude-code undoes it.

Agents / Codex

Codex

$ ms connect codex --env STRIPE_API_KEY=ms://stripe/test

Sets Codex's shell environment policy, network proxy and an mcp_servers.ms entry. For run mode, have Codex call ms run -- <command> or use the MCP tools.

Agents / MCP

MCP

ms mcp is a stdio MCP server that turns your run commands into typed tools, such as db_query or deploy_staging. It's a thin client of msd and never holds a value.

Cursor and Gemini connectors are next. planned

Reference / Security model

Security model

On macOS the agent and msd run as the same Unix user, so every control assumes the agent can read your files and reach the daemon's socket.

An agent tries toWhy it fails
Read a value from the keychainItems are bound to msd's code signature: identifier cc.morsec.msd plus the release team. Another program, or a replaced msd, can't read them.
Read msd's memoryHardened runtime without get-task-allow. Values are zeroized after use.
Loosen the rules fileRules are MAC'd with a vault key; a bad MAC is rejected. Loosening needs ms rules and Touch ID.
Fake an approvalPrompts come from the real exec plan, on your terminal, with Touch ID. Callers inside an agent session can't approve.
Pose as msdA signed ms checks msd's signature and that msd alone holds the socket.
Rewrite receiptsHash-chained and MAC'd; ms log --verify finds the edit.
Run ms dev, or open the dashboard, to get valuesBoth refuse inside an agent session, ms dev refuses agent programs, and the dashboard refuses connections from agent processes. Each ms dev run and each value shown needs your Touch ID.
Skip the proxyIt never had a value, so it only loses access. ms doctor reports the drift.

Known limit. In run mode, a same-user process could read a child command's environment or passfile while it runs. morsec prefers protocols that never put the value in a child (SSH agent, git credential helper) and keeps passfiles short-lived. Running children as a separate user is on the roadmap. The same holds for the values ms dev puts in your app's environment.

The full threat model maps 110 threats to the tests that cover them: docs/threat-model.md.

Reference / Upgrading

Upgrading

There is no auto-update. Upgrade with the channel you installed with, then restart msd:

$ brew upgrade morsec          # or npm install -g morsec@latest, or the curl installer$ launchctl kickstart -k gui/$(id -u)/cc.morsec.msd

ms and msd ship together: always upgrade both and restart msd, or an older ms may not understand the new msd (for example ms approve). After a curl upgrade, also run ms run --link-shims. If you switch Node versions with nvm, fnm or volta, install morsec under the new one, run ms init and reconnect your agents.

Reference / Troubleshooting

Troubleshooting

Start with ms doctor. It checks the daemon, the vault, the run shims and every connected agent, and each failure says what to run.

You seeDo this
daemon not runningms start, or check ms doctor.
A request to a new host is blockedms rules <key> --add-host <host>, then retry.
The agent still sees an old valueStart a new agent session after ms connect.
msd doesn't start after an upgradelaunchctl kickstart -k gui/$(id -u)/cc.morsec.msd
ms dev warns about your Node version, or API calls fail with a reference in themUse Node 24 or later. Older Node ignores HTTPS_PROXY, so references go out unswapped.
ms dev, ms set, ms approve or ms dashboard says it is refused in an agent sessionYou're inside an agent session. Run it from your own terminal.
ms doctor lists keys stored by another morsec buildThe keychain lets only the build that stored a key read or delete it, typically a dev build from before you installed the release. Remove each with the command ms doctor prints: security delete-generic-password -s cc.morsec.vault -a <name> (it asks for your login password).
ms rm is refused because a project still refers to the keyms undo <project> --key <key> puts the value back in the .env first, or use ms rm --force.
